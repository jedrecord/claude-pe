Engineering Economics

Cheap Agents, Expensive Judgment

Frontier model prices keep climbing, and inference has become the dominant recurring cost in the AI budget — one teams routinely under-forecast. A small orchestrator pattern called claude‑pe offers one way to keep paying for judgment without paying for it on every task.

Anthropic API list pricing per million tokens, September 2026 (claude.com/pricing). Opus 5.5 runs 4× Haiku's rate on both sides of the ledger — and it's already 20% cheaper than Opus 5's $5 / $25.

The line item nobody budgeted for

Two years ago, "AI spend" on an engineering budget meant seats and API credits, rounding error next to payroll. That's no longer true. RapidData's State of Enterprise AI 2026 calls inference the dominant recurring cost in enterprise AI budgets — one that organizations routinely under-forecast by 3–5x. ISG's 2025 IT budget study, published back in December 2024, tells a similar story from a different angle: overall IT budgets were projected to rise a modest 1.8%, but AI spending inside those budgets was projected to rise 5.7%, soaking up nearly a third of the total IT budget increase by itself.

None of this is because engineers got careless. It's because the work got better, and better work asks harder questions of bigger models, more often, in longer agentic loops that weren't part of anyone's cost model eighteen months ago. A model that plans, delegates, checks its own output, and retries is doing four or five times the token work of one that just answers a prompt. Multiply that by a team running agents all day, and the invoice stops looking like rounding error.

The obvious fix — use the frontier model for everything, it's the best one — is also the expensive one. The less obvious fix is to ask a sharper question: which parts of this workflow actually need frontier judgment, and which parts just need a competent model that follows instructions?

One idea, doing most of the work

That question has an answer that shows up across every serious cost-reduction result in this space: separate planning from execution, and spend your expensive tokens only on the planning. A frontier model is genuinely worth its price when it's deciding what to do, breaking down ambiguous work, or judging whether a result is actually correct. It's usually wasted when it's writing boilerplate, running a test suite, or formatting a research summary — tasks a much cheaper model handles at a similar quality bar.

This isn't a hunch. UC Berkeley's peer-reviewed RouteLLM showed that routing between model tiers by query difficulty cut costs by roughly 85% while holding onto 95% of GPT-4-level quality. AWS reports similar results in production with Bedrock's Intelligent Prompt Routing, around 60% savings. Independent surveys of commercial routing platforms report a wide band, roughly 40–85% cost reduction, depending on workload and how aggressively the router shifts work downward.

A caveat worth sitting with

That band is real, but it isn't automatic. LLMRouterBench (ACL 2026) put a wide set of routing methods — commercial products included — through a unified evaluation and found many of them don't reliably beat a simple baseline like "always use the mid-tier model." Routing helps when the split between easy and hard work is real and the router can tell the difference. It doesn't help by existing. Measure your own workload before you bank the savings.

Hal: an orchestrator that refuses to do the work

claude‑pe is a small, working implementation of that idea, built around a single rule: the orchestrator — nicknamed Hal — never does substantive work itself. It only receives a request, decides which specialist should handle it, dispatches the task, and reports back. Every actual line of code, every test run, every piece of research is done by one of seven named sub-agents, each with a narrow job description.

Notice the split. The agents doing routine execution — writing code, running research, filing test results — sit on Haiku. The agents doing judgment — deciding whether a task is actually complete, red-teaming a plan before it ships, unsticking a confused peer — sit on Opus, alongside Hal itself. The pattern isn't "cheap model bad, expensive model good." It's routing each kind of thinking to the tier that can actually do it well, and refusing to pay Opus rates for Haiku-shaped work.

Setting it up

The orchestrator pattern alone helps, because it stops one expensive context from doing everyone's job. claude‑pe adds a second lever on top: a local model proxy that can reroute the "cheap" tier away from Anthropic's API entirely, onto open-weight models, without touching a single agent definition.

Clone the repository and install LiteLLM, which acts as the translation layer between Claude Code's Anthropic-formatted requests and whatever backend you actually want serving them:

Terminal

git clone https://github.com/jedrecord/claude-pe.git
cd claude-pe
uv tool install litellm

The fastest way to get running is with an OpenRouter API key and one of the bundled config profiles — no YAML to write by hand:

Terminal (continued)

export OPENROUTER_API_KEY="sk-or-xxxxxxx"
mkdir -p ~/.config/litellm
cp proxy/configs/split-nemo.yaml ~/.config/litellm/config.yaml

If you'd rather see how that mapping works, or write your own, a LiteLLM config just maps each model name in your agents' frontmatter to a real backend. Opus stays pointed at Anthropic directly — it's the planning tier, and there's no reason to substitute it. The Haiku and Sonnet execution-tier slots, used by the sub-agents, get routed to the same open-weight model on OpenRouter instead:

~/.config/litellm/config.yaml

general_settings:
  forward_llm_provider_auth_headers: true

model_list:
  - model_name: claude-opus-5-5
    litellm_params:
      model: anthropic/claude-opus-5-5
      api_key: os.environ/ANTHROPIC_API_KEY
      api_base: "https://api.anthropic.com"
  - model_name: claude-haiku-4-5-20251001
    litellm_params:
      model: openrouter/nvidia/nemotron-3-ultra-550b-a55b:free
      api_key: os.environ/OPENROUTER_API_KEY
      api_base: "https://openrouter.ai/api/v1"
  - model_name: claude-sonnet-5
    litellm_params:
      model: openrouter/nvidia/nemotron-3-ultra-550b-a55b:free
      api_key: os.environ/OPENROUTER_API_KEY
      api_base: "https://openrouter.ai/api/v1"

Beyond split-nemo.yaml, the repo's proxy/configs/ directory has more profiles ready to go — all-local Ollama profiles, split configs across DeepSeek, GLM, Kimi, and Qwen, plus a fallback chain for when a free-tier OpenRouter model gets rate-limited mid-task. Point litellm_params.model at whichever backend fits your risk tolerance; the agent definitions never need to know.

Then start the proxy and launch Claude Code against it. The bundled script handles both in one command:

scripts/claude-proxy.sh (excerpt)

litellm --config ~/.config/litellm/config.yaml --port 4000 &
export ANTHROPIC_BASE_URL="http://localhost:4000"
export ANTHROPIC_API_KEY="sk-dummy"
claude "$@"

Claude Code still addresses its agents by ordinary Anthropic model names — claude-haiku-4-5-20251001, claude-opus-5-5 — because that's what's declared in each agent's frontmatter. LiteLLM intercepts the request and silently swaps in whatever the config maps it to. Hal keeps orchestrating exactly as before; it has no idea Devon is now running on an open-weight model on the other side of a proxy.

What this is, and isn't, proven to do

claude‑pe's own README is careful about this, and it's worth being just as careful here: the cost benefit is stated as a hypothesis, not a measured result. Splitting work across model tiers adds its own overhead — review passes, completeness checks, an extra round-trip through a proxy — and that overhead consumes tokens too. The architecture is a reasonable bet, well aligned with what published routing research shows works in other systems, but nobody has benchmarked this specific team of seven agents against a single-model baseline and published the delta.

So treat this as an architecture worth trying against your own workload, the same way you'd pilot any cost lever before committing budget to it: instrument it, compare it to your current single-model setup, and let your own numbers make the case Anthropic's or Berkeley's numbers can't make for you.

The real point

Model prices are not going to stop climbing, and neither is the amount of agentic work engineering teams ask models to do. Inference is well on its way to sitting next to compensation as a line item that finance actually watches, not a rounding error folded into "cloud." The teams that manage that line well won't be the ones who found the single cheapest model and used it everywhere — quality suffers exactly where it can't afford to. They'll be the ones who figured out, task by task, which decisions genuinely need frontier judgment and which just need a model that can follow instructions. Everything else is implementation detail. claude‑pe is one implementation, offered as a starting point, not a prescription.
